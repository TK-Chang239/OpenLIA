# v2.3 Equity Research Engine — Autonomy & Integrity Roadmap

**Date opened:** 2026-05-24
**Branch context:** ongoing work on `feat/equity-research-v2.3-*`
**Status overview:** Phase 0 in progress; Phases 1–3 not yet planned; methodology adherence parked as research question.

---

## The diagnosis (one sentence)

v2.3 built the integrity half of the engine well and skipped the autonomy half — the user-uploaded template is persisted on `ReportState` but never read by any stage, so every prompt grew compensatory hardcoded defaults to fill the value vacuum.

## The philosophy this roadmap is enforcing

- **Values** are content choices (sections, methodologies, chart types, citation counts). The engine never hardcodes them — they come from the user template and the model's judgment.
- **Invariants** are integrity properties (numbers trace to sources, charts plot researched data, sections don't contradict, same figure renders the same everywhere, arithmetic runs as deterministic code). The engine MUST enforce them.
- **Constraint on dishonesty is not constraint on autonomy.** That's the trade. Pricing autonomy and integrity correctly is the whole job.

## Sequencing principle

Re-ranked by risk after reviewer pushback: **live correctness failures before flexibility improvements.** Phase 0 closes a live integrity hole (fabricated numbers can ship today); Phases 1–3 unlock autonomy / fix overreach but don't ship anything wrong today.

## Phase 0 — Number-origin discipline (COMPLETE, 2026-05-24)

**Plan:** `docs/superpowers/plans/2026-05-24-phase-0-number-origin-discipline.md`
**Commits:** `394d84ac` through `075700da` on `feat/equity-research-v2.3-ui` (18 commits, 8 tasks + cleanup).
**Tests:** 218/218 in `packages/core/tests/test_runtime/test_report_v2_3/`.

**Rule shipped:** every number in the body is either a sourced fact, a computed fact, or an explicitly-labeled estimate — never naked model output.

**Mechanisms shipped:**
- `EstimateSource` as fifth `Provenance` variant (analyst judgment with explicit basis); bundle validator walks its `derived_from` chain identically to `ComputedSource`.
- Three writer-time markers: `{{CITE:...}}` (existing), `{{DERIVE:method|inputs|new_id}}`, `{{ESTIMATE:new_id|value|unit|basis}}`.
- Deterministic mint step (`stages/_mint.py::mint_inline_facts`) resolves DERIVE/ESTIMATE into `BundleFact`s before VERIFY sees the body; dedup tracks marker content so cross-type id collisions fail loud.
- Deterministic `UNCITED_NUMBER` check (`stages/verify.py::_check_uncited_numbers`) flags any digit-bearing token outside markers + exempt set (years, FY tokens, quarters, ordinals). VERIFY LLM prompt cedes `uncited_number` and `value_mismatch` to the deterministic checks.
- Derivation library (`derivations.py`): `growth_rate`, `yoy_delta`, `ratio` — pure math returning `BundleFact` with `ComputedSource`. `DerivationFn` Protocol types the registry.
- WRITE_SYSTEM_PROMPT teaches the three-marker grammar with a worked example in positive phrasing.

**Design decisions resolved:**
- Population path: on-demand mid-WRITE via inline markers (rejected: speculative COMPUTE-time emission — wasteful and can't mint estimates which are inherently write-time judgment).
- Derivation library scope: `growth_rate`, `yoy_delta`, `ratio` (covers what writers actually claim; larger math like DCF stays in `valuation/`).

**Known follow-ups (Phase 0 ship-ready without these; addressable in a small Phase 0.1 PR):**
- `ratio` unit rendering: returns `unit=None`, so a writer using `{{DERIVE:ratio|gross_profit,rev_ttm|gross_margin}}` gets `"0.60 [^N]"` instead of `"60.0%"`. Cleanest fix: split into `ratio_percent` / `ratio_multiple` / `ratio_pure` so the writer picks the unit semantic at marker-time, OR extend the DERIVE grammar with an optional `unit` slot.
- `DerivationFn` Protocol params `current`/`prior` don't match `ratio`'s `numerator`/`denominator` — rename Protocol params to `a`/`b` to satisfy mypy.
- `_check_uncited_numbers` doesn't strip DERIVE/ESTIMATE markers (only CITE/FIG). In real flow this is unreachable because WRITE's mint step resolves them first; add as defense-in-depth.
- `MintError` lives in private `stages/_mint` — export from `stages/__init__.py` so callers can catch it specifically.

## Phase 1 — Pass the user template text through every stage (COMPLETE, 2026-05-24)

**Plan:** `docs/superpowers/plans/2026-05-24-phase-1-template-plumbing.md`
**Commits:** `0300f32c` through `b2df1bd6` on `feat/equity-research-v2.3-template-plumbing` (14 commits, 10 tasks + final cross-cutting fixes).
**Tests:** 247/247 in `packages/core/tests/test_runtime/test_report_v2_3/`.

**Rule shipped:** the user template is the source of truth for report structure. Every stage receives a `TemplateSpec` via its Request dataclass; PLAN strictly follows the template's section list; CLARIFY/SYNTHESIZE/WRITE consume the template's per-section intent to ground LLM output in the user's intent.

**Mechanisms shipped:**
- New `templates/` module with structured `TemplateSpec` + `SectionSpec` Pydantic schema (`spec.py`) and five built-in instances + `get_builtin(rt)` lookup (`builtins.py`).
- `ReportState.template: TemplateSpec` (required, no default).
- Server wiring (`v2_3_run_service.start_run`) auto-populates `state.template` from `get_builtin(report_type)`.
- CLARIFY: `_BUILTIN_TEMPLATE_SHAPES` dict deleted; consumes `request.template.shape_description`.
- PLAN: strict template adherence. `PLAN_SYSTEM_PROMPT` rewritten ("invent outline" → "fill in template"); `_coerce_outline_to_template` helper rebuilds section structure (id, title, section_type) from the template while preserving the LLM's `data_needs` for matching sections.
- SYNTHESIZE: per-section `template_intent` enriches the synthesizer payload; one positive-phrasing sentence in `SYNTHESIZE_SYSTEM_PROMPT`.
- WRITE: per-section `section_intent` surfaces in the writer payload; one positive-phrasing sentence in `WRITE_SYSTEM_PROMPT`.
- RESEARCH/COMPUTE/VERIFY: pass-through plumbing — `template` field added on each `*Request` for symmetry, with inline comment explaining why.

**Design decisions resolved:**
- `TemplateSpec` is structured Pydantic, not a free-text blob (anchored to deterministic outline derivation).
- PLAN adherence is STRICT — outline structure comes from template; LLM only authors `data_needs` (and `valuation_plan`). The coercer backstops LLM drift.
- Built-ins are the only template source in Phase 1; user upload deferred to Phase 1.5.
- Methodology adherence verification stays out of scope as a research question.

**Known follow-ups (Phase 1 ship-ready without these; nice-to-haves for a future PR):**
- `SectionSpec.id` / `TemplateSpec.template_id` slug pattern is underscore-only (`^[a-z0-9_]+$`). Consistent with v2.3 conventions today but Phase 1.5 user uploads may want hyphen support — revisit when adding upload UI.
- `SYNTHESIZE_SYSTEM_PROMPT` rule text saying "Each outline section carries a `template_intent` field" could be more explicit about it being on the INPUT (vs an output field).
- `test_template_plumbing_e2e.py` is one function with five assertion blocks; could be decomposed into per-stage sub-tests for better CI triage.
- UNCITED_NUMBER false positive on identifier-embedded digits (e.g. `e2e` in `thesis_e2e` matches the regex's `\d`). Phase 0 follow-up territory — would need regex to require non-identifier context around the digit.

## Phase 2 — Excise the prescriptions now redundant (COMPLETE, 2026-05-24)

**Plan:** `docs/superpowers/plans/2026-05-24-phase-2-excise-prescriptions.md`
**Commits:** `ce332e1a` through `692d1321` on `feat/equity-research-v2.3-excise-prescriptions` (10 commits, 7 tasks + final review follow-ups).
**Tests:** 257/257 in `packages/core/tests/test_runtime/test_report_v2_3/`. 2103/2103 server suite.

**Rule shipped:** content prescriptions that the template now makes redundant, that a Phase 0/1 deterministic check already covers, or that expressed arbitrary engine opinions (UX caps, word budgets) are gone from v2.3 prompts. The LLM's autonomy increased everywhere these prescriptions were deleted; structural integrity unchanged.

**What was deleted:**
- `MAX_CLARIFY_QUESTIONS = 3` cap (schemas constant + validator + prompt mention)
- NVDA-specific examples in CLARIFY, PLAN, COMPUTE, WRITE, and RESEARCH prompts — replaced with `<TICKER>`/`<COMPANY>`/`<PEER_TICKER>` placeholders
- 20-word hard cap on `central_argument` in SYNTHESIZE
- ~50-line chart-selection guide + anti-patterns block in SYNTHESIZE (VISUALIZE already enforces renderability deterministically)
- Per-length word budgets (150-250 / 300-500 / 600-900) in WRITE
- ~10 content-prescriptive negatives across PLAN/SYNTHESIZE/WRITE/COMPUTE/RESEARCH/CLARIFY prompts rewritten as positive equivalents

**What was preserved (correctly):**
- Schema-level enum constraints expressed as "MUST" — accurate API contract, not opinion
- Output-format constraints ("Output JSON only. No prose, no markdown fences.") — protocol requirement
- Docstrings and Python comments containing negatives — developer-facing, not LLM-facing
- All Phase 0 integrity invariants (provenance, deterministic UNCITED_NUMBER, mint helper, resolve() substitution)
- All Phase 1 template-driven flow (PLAN coercer, template_intent in SYNTHESIZE/WRITE payloads, section_intent in WRITE prompt)

**Architecture:** no schema changes (beyond MAX_CLARIFY_QUESTIONS deletion), no new modules, no behavior-changing code beyond prompt strings. Pure surgery, regression-pinned with deletion tests.

**Scope decision deferred to Phase 3:** the forced-ticker question in CLARIFY ("most v2.3 stages assume at least one subject ticker") stays for now — it's coupled to `TemplateSpec.ticker_anchored` consumption and `Outline.tickers: min_length=1` relaxation, both Phase 3 work.

## Phase 3 — Broaden brittle invariants (COMPLETE, 2026-05-25)

**Plan:** `docs/superpowers/plans/2026-05-24-phase-3-broaden-invariants.md`
**Commits:** `5c443f6e` through `59cfec87` on `feat/equity-research-v2.3-broaden-invariants` (6 commits, 5 tasks + final review follow-ups).

**Rule shipped:** the schemas, builtins, CLARIFY prompt, and RESEARCH check no longer over-narrow what counts as a valid v2.3 run. Sector primers and macro themes — reports with no specific subject ticker — now flow through the pipeline cleanly. `TemplateSpec.ticker_anchored` is now the single source of truth for whether a run requires a subject ticker.

**Mechanisms shipped:**
- `Outline.tickers` and `ResearchBundle.tickers` relaxed from `min_length=1` to `min_length=0` (`schemas.py`).
- `_SECTOR_RESEARCH` builtin flipped to `ticker_anchored=False` (`templates/builtins.py`). Other builtins (INITIATION/UPDATE/EARNINGS_REVIEW/MORNING_BRIEF) stay True — inherently single-name.
- CLARIFY prompt + user payload consume `template.ticker_anchored`; forced-ticker question for topic-only prompts is now conditional on the flag (`clients/llm_clarifier.py`).
- RESEARCH non-empty raise gated on `planner_asked_for_facts` (any section's data_needs non-empty); thematic runs with empty data_needs return empty bundles cleanly while broken research with non-empty data_needs still raises (`clients/llm_researcher.py`).
- End-to-end test proving a ticker-less custom template runs through PLAN/SYNTHESIZE/WRITE/VERIFY without raising (`test_tickerless_e2e.py`).

**Out of scope (deferred):**
- ~~`ChartType` enum widening (add `table`, `heatmap`)~~ — shipped in Phase 3.1 (see below).
- User-template upload UI: Phase 1.5 work, separately scoped.
- Methodology adherence verification: parked as research question.

**Known follow-ups (Phase 3 ship-ready without these; small drive-bys for a future PR):**
- `MORNING_BRIEF.ticker_anchored` is debatable — the shape_description says "overnight signals that should reshape today's watchlist," which is market-wide rather than name-specific. Conservative default of True works; revisit when there's real usage signal.
- `test_tickerless_e2e.py` skips RESEARCH, CLARIFY, and ASSEMBLE for simplicity. A true runner-driven e2e covering CLARIFY's `ticker_anchored=False` branch end-to-end would give higher confidence, but the unit tests in `test_llm_clarifier.py` cover that branch.

## Phase 1.5 — User template upload (COMPLETE, 2026-05-25)

**Plan:** `docs/superpowers/plans/2026-05-25-phase-1.5-template-upload.md`
**Commits:** `e97f72db` through `5494e88e` on `feat/equity-research-v2.3-template-upload` (7 commits, 7 tasks + final review follow-ups).
**Tests:** 18/18 new backend tests (9 compile + 3 v23/parse + 4 start_run + 2 e2e/cross-owner), 5/5 new frontend modal tests; full server suite stays green.

**Rule shipped:** users can upload custom v2.3 report structures (markdown, with optional YAML frontmatter) and launch v2.3 runs that use them as `state.template` in place of the report_type built-in. Closes the loop opened by Phase 1: the `TemplateSpec` rails were built explicitly so user-uploaded templates could replace `get_builtin(report_type)` at run-launch time.

**Mechanisms shipped:**
- `compile_v23_spec` service (`services/template_compile_v23.py`) — pure deterministic mapping of `ParsedTemplate` (sections + frontmatter from the existing `parse_template`) to a v2.3 `TemplateSpec` dict.
- `POST /api/report-templates/v23/parse` — exposes the v2.3 compile path; returns 200 with `validation_errors` array so the UI can render them inline next to the parsed structure.
- `v2_3_run_service.start_run` accepts optional `template_id`; new `_resolve_template` helper: None → `get_builtin(report_type)`; UUID → owner-scoped row from `report_templates`, validate as `TemplateSpec`. 404 cross-owner (no existence leak); 422 on invalid v2.3 shape with "re-upload via v2.3" message.
- `V23TemplateUploadModal` (`components/equity-research/V23TemplateUploadModal.tsx`) — paste markdown, parse via v2.3, preview sections, save via existing CRUD. Auto-resets on each reopen.
- V23Composer accepts `templateId` prop; threads it into the launch payload. EquityResearch.tsx mounts the existing `FrameworkTemplatePicker` on both v2.2 and v2.3 paths and auto-selects newly-uploaded templates.

**Infrastructure reused (from PR 13, May 2026):**
- `report_templates` table + Alembic migration
- `ReportTemplate` SQLAlchemy model
- CRUD routes (`/api/report-templates`)
- `parse_template` deterministic markdown→ParsedTemplate parser
- `ingest_document` (docx → markdown via mammoth)
- `FrameworkTemplatePicker` component
- Most of `report-templates.ts` API client

**Scope decisions resolved:**
- One PR with backend + frontend (backend-only invisible to users).
- Reuse existing CRUD endpoints — only added the v23 parse variant.
- Deterministic parser sufficient — no LLM call at upload time.
- No schema-version column on the table — v2.3 validation at start-run time; mismatched rows 422 with a clear message.
- No edit-in-place; upload-replace is the v1 UX.
- Picker shows all user templates regardless of schema shape; v2-shaped rows picked for v2.3 runs get a clear 422 from the backend. Adding a v2-vs-v2.3 badge in the picker is a follow-up.

**Known follow-ups (Phase 1.5 ship-ready without these):**
- Picker doesn't visually distinguish v2-shaped vs v2.3-shaped templates. Users find out at run-launch time via the 422 message. A "validated for v2.3" badge or filter would prevent the discovery-via-error pattern.
- The upload modal is paste-only (no file picker). The existing `/api/report-templates/ingest` endpoint accepts docx/md/txt and converts to markdown; wiring a file picker into the modal is a small follow-up.

## Phase 3.1 — ChartType widening (COMPLETE, 2026-05-25)

**Branch:** `feat/equity-research-v2.3-chart-types-widen`
**Tests:** all 1440 tests in v2.3 core + server suites pass; 4 new tests (2 sanitiser/prompt, 2 renderer).

**Rule shipped:** the SYNTHESIZE LLM can now pick `heatmap` or `table` in addition to the original six chart types. Both render through the existing docx pipeline:
- `HEATMAP` — matplotlib `imshow` grid where rows = series, columns = categories; per-cell numeric labels on a Red-Yellow-Green colormap. Designed to land sensitivity-style grids without bespoke data plumbing.
- `TABLE` — skips the matplotlib PNG entirely; the native docx data-table that every chart already gets becomes the figure on its own. Chosen when a numeric grid (peer comp, key-metric snapshot) reads better than a plot.

**Mechanisms shipped:**
- `ChartType` enum extended with `HEATMAP = "heatmap"` and `TABLE = "table"` (`schemas.py`); docstring rewritten to describe the rendering paths.
- `_VALID_CHART_TYPES` in `llm_stage_clients.py` extended; SYNTHESIZE_SYSTEM_PROMPT now lists eight legal values + a one-sentence picking-guidance line.
- `try_render_chart_png` short-circuits `TABLE` to `None` (caller already emits the data table). New `_draw_heatmap` branch handles `HEATMAP`; the legend-emit guard skips `HEATMAP` since the colormap is the legend.

**Out of scope (carried forward):**
- Dedicated sensitivity-result plumbing — the LLM has to express the grid as N series × M categories at SYNTHESIZE time rather than referencing a `SensitivityResult` fact directly. Wiring `SensitivityResult.grid` into a heatmap as a single-fact reference is a follow-up if real runs show the LLM struggling with the per-row decomposition.

## Out of scope — Methodology adherence verification

**Status: parked as a research question, not a deliverable.**

The audit's original wishlist included "verify the methodology the template asked for was actually followed." On reflection (per reviewer feedback), this likely does not reduce to a deterministic check — it's closer to the LLM-verifier problem (semantic intent matching) than the `resolve()` problem (structural reference resolution).

**Current position:** methodology adherence remains an LLM-verifier-client check (fallible, soft). Document this as a known limitation. Add targeted structural checks ONLY when a specific methodology has a structural footprint we can assert on (e.g., template says `compute_methods: ["dcf"]` → assert `dcf_*` facts exist in the bundle).

Do NOT promise a general deterministic methodology verifier we can't deliver.

## Anchoring notes for future sessions

- The audit conversation that produced this roadmap exchanged four review rounds with the user — each round sharpened priorities (live correctness > flexibility; use `ComputedSource` instead of new helpers; split pass-text from enforce-adherence; add `EstimateSource` so judgment numbers have an honest origin).
- The reviewer's load-bearing insights worth preserving:
  - "The overreach is a symptom; missing template is the disease."
  - "The engine doesn't verify cited values are correct; it makes the citation BE the value."
  - "Equity research IS judgment — a rule that admits only sourced + computed facts is too strict to ship."
- The first three insights inform Phase 1. The last one drove the `EstimateSource` addition in Phase 0.
